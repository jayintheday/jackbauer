# Jack Bauer report — Meridian weekly digest — 2026-10-30

## Verdict
No. The last two digests were wrong and the pipeline reported success both times. On 20 Oct partners got invented summaries for two clients whose PDFs had no extractable text. The same digest headlined a 3.4% day-rate change; the pricing CSVs in the repo give +0.76%. On 27 Oct the Claude call failed in 4 seconds, the script swallowed the error, and partners got an email whose whole body was "Weekly digest". The job still said "Job succeeded". **Fix first:** make `summarise.py` fail loudly (log the exception, exit non-zero, drop the fallback digest and `continue-on-error`) so a broken week stops looking like a quiet one.

## Pipeline map
1. GitHub Actions cron `0 8 * * 1` (UTC) → job `digest` · evidence: `logs/actions-run-*.log` (2 runs)
2. `scripts/fetch_reports.py` (Python; Notion DB query + HTTP GET per client) → `reports/*.pdf`, `clients.json` (never read) · evidence: "fetched N clients"
3. `scripts/extract.py` (pypdf, 12,000-char cap) → `text/*.txt` · evidence: "extracted N chars"
4. `scripts/summarise.py` (one Anthropic Messages call, `claude-3-opus-latest`, no tools). Instruction stack: system = `prompts/system.md`; user = `reference/style-guide.md` + `text/*.txt` + `data/pricing/*.csv`. **`AGENTS.md` is never loaded.** → `digest.json` · evidence: `logs/digest-artifact-*.json`
5. curl → n8n webhook → Format → Slack `#partners-digest` + Gmail partners@ · evidence: `logs/partners-email-2026-10-27.txt`. n8n saves no executions (unseen).

## A. Instruction conflicts
### A1. Prompt orders the model to invent missing client data — Critical · Silent · Confirmed
- **Where:** step 4, `prompts/system.md:10`; the opposite rule (`AGENTS.md:5` "Never invent figures") is never loaded (no reference to it anywhere in `scripts/`, `.github/` or `n8n/`)
- **Evidence:** `2026-10-20T08:02:04Z extracted 0 chars from Halden Logistics.pdf`, yet the digest says Halden "recently announced a new automated hub in the Midlands…"; Quarry Lane (also 0 chars) is "likely benefiting from easing mortgage rates…"
- **Why it's silent:** the text reads fluently; only a partner who knows the client would catch it.
- **Fix:** delete line 10; make `system.md` the only owner of the rules and require "no report this week" (15 min).

### A2. Output contract lives only in the unloaded AGENTS.md; prompt asks for markdown — High · Silent · Confirmed
- **Where:** step 4→5, `system.md:3,12` ("markdown headings for each client" … "Return it in the JSON format the distribution step expects"); the schema exists only in `AGENTS.md:3`
- **Evidence:** 20 Oct `"headline": "## Monday digest — a steady week"`: markdown leaked into a JSON field. A parse failure falls back silently (see C1).
- **Fix:** put the schema in the prompt and use structured output or schema validation (30 min).

### A3. "Check the latest news online", but the call has no tools — High · Silent · Confirmed
- **Where:** step 4, `system.md:8`; `summarise.py:24-29` passes no `tools`
- **Evidence:** the Halden "recently announced" claim above has no source; it can only come from model memory.
- **Fix:** delete the line, or add web search and require a cited URL per claim (5 min). (B6 → here.)

### A4. Length rules conflict and the output cap is too small — Medium · Silent · Latent
- **Where:** `system.md:4` "thorough paragraph — partners prefer detail" vs `AGENTS.md:4` "under 60 words"; `summarise.py:26` `max_tokens=2000`
- **Evidence:** 20 Oct parsed, so no truncation has happened yet. Once B1/B2 are fixed and ~100 clients reach the model, thorough paragraphs will overrun 2,000 tokens, the JSON will be cut off, and C1's fallback will fire.
- **Fix:** one 60-word rule; size `max_tokens` to client count; log `stop_reason` (10 min).

## B. Retrieval & tools
### B5. Pricing headline computed by the model reading 1,280 rows — Critical · Silent · Confirmed
- **Where:** step 4, `system.md:6`; `summarise.py:16` pastes four CSVs with values like `"£1,154"`
- **Evidence:** 20 Oct digest `"pricing_total_change_pct": 3.4`. Recomputed in code from `data/pricing/*.csv`: **+0.76%** (operations 0.77, people 0.85, strategy 0.64, technology 0.77). The repo has one commit (2026-09-08) and no step writes `data/pricing/`, so the 20 Oct run read these same files. Caveat: assumes the GitHub copy matches this local one.
- **Fix:** compute in Python, pass the number in, have the model only narrate it (30 min). Also: nothing refreshes the CSVs, so "this week's pricing moves" is the same file every week. Confirm who updates it.

### B2. 95 of 100 clients never reach the digest, with no record why — High · Silent · Confirmed (cause Suspected)
- **Where:** step 2, `fetch_reports.py:37-43` (`continue` on no URL, `except RequestException: pass`, no status check); `clients.json` is written at `:44` but never read
- **Evidence:** both runs: "fetched 100 clients", then only 5 "extracted" lines and no "skip" lines. The digest has no way to say "no report this week" for the other 95.
- **Fix:** carry a per-client status into the prompt; `raise_for_status`; print a drops-by-reason count; fail above a threshold (1 h).

### B3. Image-only PDFs extract to 0 chars and nothing flags it — High · Silent · Confirmed
- **Where:** step 3, `extract.py:14-20`. An empty `.txt` is written and sent as a bare `### Name` heading.
- **Evidence:** Halden and Quarry Lane at 0 chars on both runs. Combined with A1, this produced the invented summaries.
- **Fix:** if chars < threshold, OCR the PDF or mark it "no readable report" (hours).

### B4. Reports silently cut to 12,000 chars; the log shows the uncut size — High · Silent · Confirmed
- **Where:** step 3, `extract.py:19` `text[:MAX_CHARS]` vs `:21` logs `len(text)`
- **Evidence:** `08:02:06Z extracted 48211 chars from Northgate Utilities.pdf`: ~75% dropped (51,877 on 27 Oct). Northgate is absent from the 20 Oct digest.
- **Fix:** log kept/total and a truncation marker; summarise each report in its own call (hours). (D1 → here.)

### B1. Notion query reads only the first page — High · Silent · Suspected
- **Where:** step 2, `fetch_reports.py:16-24`; one POST, no `has_more`/`start_cursor` handling
- **Evidence:** exactly 100 clients on both runs, which is Notion's page cap. Confirm by counting Active rows in the DB.
- **Fix:** loop on the cursor; assert the count (15 min).

**Low:** B6 → see A3. A client name with `/` would break the PDF path (`fetch_reports.py:41`).

## E. Token efficiency
No usage is recorded (`summarise.py:30` discards `msg.usage`). Figures below are **estimates** at ~4 chars/token for the 27 Oct input.

| Component | Chars | Est. tokens | Share |
|---|---|---|---|
| `data/pricing/*.csv` | 43,368 | ~10.8k | 39% |
| Report text (3 reports + 2 empty) | ~32,960 | ~8.2k | 30% |
| `reference/style-guide.md` | 32,776 | ~8.2k | 30% |
| `prompts/system.md` | 707 | ~0.2k | <1% |
| **Total** | ~109.8k | **~27.5k** | |

- **Cuts:** style guide → one paragraph (−8.1k, no quality risk); pricing → one computed number (−10.7k, improves accuracy). Together they cut input by ~68%.
- **Cache:** the job runs weekly, beyond any cache lifetime, so caching is not a lever. The Batch API is optional once the job is healthy.
- **Model fit:** after the cuts this is ~8k tokens summarised into short JSON. Try a current Sonnet-tier model against a strong one on two weeks of reports before choosing.
- **Logging:** print `usage` and `stop_reason` to stderr so future audits have real numbers.

## What's working
- `extract.py` writes atomically (tmp + `replace`), so no half-written text files.
- The Notion query calls `raise_for_status()`, so an expired Notion token would fail loudly.
- Explicit timeouts on every HTTP call and a 30-minute job timeout.
- `digest.json` is uploaded as an artifact each run. That's the only reason the 27 Oct failure was traceable. Keep it.
